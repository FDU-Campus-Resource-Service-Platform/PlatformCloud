# PlatformCloud 模块边界

本文档约束 `PlatformCloud` 的模块职责、服务边界和跨服务调用方式。修改业务代码前，应先确认改动属于哪个模块，不要把其他服务的实现细节搬进当前服务。

## 1. Maven 模块形态

- 根目录 `pom.xml` 是 Maven 聚合工程，统一管理版本、依赖和插件。
- `platform-common` 是当前唯一的公共模块，承接跨服务共享的基础类型、工具、安全上下文、公共异常处理与审计等基础能力；具体实现按需求逐步补齐。
- 当前没有独立的 common-log、system 或其他基础服务模块。
- 各业务服务通常包含 `*-api` 与 `*-biz`：
  - `*-api` 放对外契约、DTO、Base、枚举、常量、Feign 接口和 MQ 消息类型。
  - `*-biz` 放运行时实现、Controller、Service、Mapper、Repository、Consumer、Task、配置和服务内错误枚举。
- 只有没有对外 API 契约的服务可以只有 `*-biz`，但新增跨服务调用前应先补齐清晰的 API 契约。

## 2. 服务职责

- `platform-seat-service`（M1）：自习座位搜索、预约时段、签到、违约记录和历史复用。
- `platform-classroom-service`（M2）：整教室预约的权限门槛、申请提交、多级审批（通过 / 驳回）和超时自动撤销。
- `platform-maintenance-service`（M3）：物业故障上报、派单、维修中状态、超时升级、完工验收和评价。
- D 公共层包含 RBAC 身份与权限、空间与座位主数据、通知和操作审计等职责，由 `platform-common` 与各业务服务按实际需求分工承接。

当前只保留一个 common 和三个业务服务。API 包仅初始化到基础包，Biz 仅保留启动、基础配置与健康检查测试；以上职责是后续实现边界，不表示业务能力已经实现。

## 3. 跨服务调用

- 跨服务调用优先使用已有 `*-api` 中的 Feign 接口、DTO、枚举和 MQ 消息类型。
- 不在当前服务复制其他服务的 Entity、Mapper、Repository 或内部 Service 实现。
- 不通过字符串拼装方式绕过现有 Feign/API 契约调用其他服务。
- 如果现有 API 契约不足，先扩展提供方的 `*-api`，再在消费方使用新契约。
- OpenAPI 文案只维护在 Controller；Feign 接口不维护独立 `@Tag` / `@Operation` 文案。

## 4. 公共能力归属

- 多个服务都会使用的基础类型、工具和自动配置放 `platform-common`。
- 跨服务复用的审计基础类型与工具放 `platform-common`，具体业务事件的记录留在所属服务；持久化与接收职责随实现方案明确。
- 只有某个业务域使用的常量、枚举、DTO、错误码留在对应服务。
- 不要因为一个服务内部重复两三次就上升为公共能力；公共能力应有稳定跨服务需求。

## 5. Review 检查清单

- 改动是否落在正确的业务服务和 `*-api` / `*-biz` 层级。
- 是否避免了把其他服务的实现类、表结构或内部规则搬进当前服务。
- 新增跨服务能力是否通过 API 契约表达，而不是通过实现细节耦合。
- 公共能力是否确实跨服务稳定复用，而不是过早抽象。
